# Click subdivisions: investigation and implementation plan

## Recommendation

Add four straight subdivision choices: **Beat (1)**, **2 per beat**, **3 per beat (triplets)**, and **4 per beat**. Keep BPM and the duration of a measure unchanged. Render the subdivision clicks into the existing one-measure PCM loop, with the first click of each beat clearly stronger than the intervening clicks. Preserve the current one-click pattern as the default for every existing song.

Store the Live choice on the canonical `Song`, since a setlist can contain songs with different rhythmic feels. Give Rehearse its own session choice. Do not make changing a song's subdivision silently change another song. Put the control beside time signature and tempo in the Live song editor, and beside Accent in Rehearse; show the active choice near the click state. Labels should say “per beat” because the present timing model treats each numbered unit of 6/8, 9/8, and 12/8 as a BPM beat. A separate meter project should decide whether compound meters use dotted-quarter pulses; subdivision work must not silently reinterpret existing BPMs or countoffs.

## What other products establish

- [Ableton Live 12](https://www.ableton.com/en/manual/recording-new-clips/) exposes metronome **Rhythm** as a beat division. Its default follows the time-signature denominator, and divisions that do not fit a bar are disabled. Its count-in and metronome settings share one menu. This supports an explicit, meter-aware subdivision control rather than treating 2× BPM as a substitute.
- [Logic Pro for Mac](https://support.apple.com/en-sa/guide/logicpro/lgcpe1d6118e/mac) distinguishes **bar, group, beat, and division** clicks, with separate note and velocity settings. [Logic Pro for iPad](https://support.apple.com/en-ge/guide/logicpro-ipad/lpip5c02c2a4/ipados) describes group accents in compound meter and lets users adjust metronome settings during playback. This supports a hierarchy of downbeat, beat, then division, and shows why compound-meter interpretation needs an explicit decision.
- [Soundbrenner's metronome](https://metronome.soundbrenner.com/) presents tempo, time signature, subdivisions, and accents as separate controls. Its [triplet page](https://metronome.soundbrenner.com/triplet-metronome/) defines triplets as three equal parts of a beat. Its [app manual](https://www.soundbrenner.com/pages/manual-the-metronome-app) describes saved songs and setlists. Together these support easy access to triplets and a song-specific Live choice.

These sources establish common expectations, not a universal rule for whether a 6/8 BPM denotes an eighth or dotted quarter. Sustain must make its own current behavior legible.

## Current implementation and risks

- `AudioEngine.makeClickBuffer` creates a one-measure `AVAudioPCMBuffer`, writes one 45 ms tone at each beat frame, and loops it on `clickPlayer`. This is already sample-timed and should remain the timing source. A UI timer must never generate audible subdivisions.
- `ClickSettings` currently holds only accent and countoff sound. `LibrarySnapshot` persists it; `Song` persists BPM and time signature. Rehearse has separate BPM and meter state. The present downbeat accent is optional and off by default.
- Both Live and Rehearse prepare a loop and optional countoff before activation. Counted countoff mixes one click and a spoken number at each beat. At fast tempos it falls back to a click-only countoff. The visual countoff is driven by `Task.sleep` and is not an audio clock.
- `activateClick` stops the current player and immediately starts the new prepared buffer. Rehearse uses this for live tempo/meter/accent edits; Live song edits use `startClick` similarly. A subdivision edit on that path would restart the bar and can produce an audible short or long beat. This is the main reliability issue to solve before shipping live subdivision changes.
- `scripts/AnalyzeClickRecording.swift` assumes one onset per BPM beat. It will report extra beats for subdivisions, so production verification needs a subdivision-aware analyzer.

## Implementation sequence

1. **Specify the rhythm contract.** Add a Codable `ClickSubdivision` enum with stable values for 1, 2, 3, and 4 slots per current BPM beat. Compute each onset from its absolute position in the measure, not by repeatedly adding a rounded interval. For slot zero, retain the existing `Int(Double(beat) * secondsPerBeat * sampleRate)` frame calculation; compute other slots from the same beat origin and fractional beat duration. Retain the existing measure frame count and click waveform for `Beat`, making old mode PCM-identical. The downbeat takes priority over a beat click, and a beat click takes priority over a subdivision click: one onset at each grid point. Choose the weaker subdivision gain by listening and a peak-level check; it must remain easy to hear the beat with Accent set to No Accent.
2. **Persist and display the choice.** Add the property to `Song` and update both initializers, coding keys, encode/decode, equality/hash, canonical normalization, and every song-copy/update path so another edit cannot reset it. Bump `LibrarySnapshot.currentSchemaVersion` from 3 to 4; decode a missing subdivision as `Beat` only for v1–v3 libraries, require the field in newly written v4 songs, and test the migration and round trip. This also prevents an older app from silently overwriting the new song choice. Add a Rehearse-session choice that defaults to `Beat`. Thread the selected choice through `prepareClick`, `startClick`, the PCM renderer, and the test engine. Live edits update the canonical song; Rehearse edits update only its session. Include clear accessibility labels such as “Subdivision, three per beat.”
3. **Render and count off.** Keep the exact measure length and BPM beat positions. For counted countoff, keep spoken numbers and their beat transients once per beat, without extra clicks under speech. For click-only countoff, use the selected rhythm so it previews the upcoming pattern. Make the fast-tempo spoken fallback follow that same click-only rule. The visual countoff continues to count beats, not subdivisions. This is a deliberate UX rule to verify with musicians before release.
4. **Make live changes phase-safe.** First build a small audio-engine prototype that switches a prepared subdivision pattern at the next measure boundary while the old pattern continues until then. The current `scheduleBuffer(..., options: .loops)` plus `stop()`/`play()` offers no demonstrated boundary-safe replacement; the implementation must prove a different scheduler before enabling edits during playback. Candidate: pre-rendered finite measure buffers with bounded lookahead and an audio-clock-based boundary. Measure whether its lookahead survives main-thread load and long playback; if it does not, prototype a render callback that reads preallocated immutable patterns without allocation or locks on the audio thread. The engine, rather than a `Task.sleep`, must own the boundary and report the actual audible switch to the store. Coalesce rapid edits, retain the old pattern on preparation failure, and prove exactly one downbeat and no gap at the boundary. A BPM or meter change may intentionally establish a new bar origin, but subdivision-only changes must preserve the beat grid.
5. **Make preparation and persistence transactional.** A song can be edited while `startCuedSong` or `startClick` is asynchronously preparing; those paths currently guard a generation and song/pad identity but do not check whether BPM, meter, or the new subdivision changed. Validate the entire click configuration at activation or invalidate and prepare again, so a stale buffer cannot start. Tie every pending switch to a session/song ID and generation; stopping, starting another song, changing route, or replacing the request cancels its UI effect. For a playing song, do not save a requested subdivision until the engine confirms the audible switch. If audio switches but `saveLibrary()` fails, keep the truthful audible/in-memory value and show the existing unsaved-changes error rather than claiming the choice is durable.
6. **Verify before release.** Add a pure PCM render test seam for click loops. Test every mode at 40, 72, and 220 BPM, 44.1 and 48 kHz, and all supported meters. Assert expected onset count, frame positions within one frame, measure duration, downbeat/beat/subdivision hierarchy, no doubled onset, peak below full scale, and no accidental onset at the loop seam. Test counted, click-only, and fast fallback countoffs; old JSON without the field; per-song switching; Rehearse isolation; stop/restart; stale asynchronous preparation; routing change and pad continuity. Extend the recording analyzer with expected slots and accent-tolerant onset detection, then repeat the existing two-hour isolated-click recording test for Beat, 2, 3, and 4 per beat at representative tempos. Record real output during repeated live changes and a pad+click soak run. Release only if there are no missing/doubled onsets or audible transition gaps, BPM and bar length remain correct, and the old Beat mode still passes its existing baseline.

## Decisions to settle in product review

- Confirm the four straight modes as the first release. Swing, dotted rhythms, custom accent maps, and polyrhythms are separate features.
- Confirm the countoff rule: spoken countoff stays beat-only; click-only countoff uses subdivisions.
- Confirm that compound-meter BPM semantics remain unchanged for this feature and that UI uses “per beat” labels until the meter model is revisited.
